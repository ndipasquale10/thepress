# App audit — September 2026

A full pass over the shipped app: cold start, the scoring hot path, storage,
accessibility, and the offline promise the product is built on. Measurements
were taken against Chromium via Playwright, driving the real `index.html`.

Five things shipped in this pass; the rest is written down with enough evidence
to be picked up in order. Findings already covered by
[`design-ideas.md`](design-ideas.md) and [`design-ideas-2.md`](design-ideas-2.md)
are not repeated here except where this pass changed what we know about them.

---

## Shipped

### 1. The app could not open on a course with no signal

The headline defect, and it sat directly under the product's core claim.

Three Firebase CDN bundles were plain `<script src>` tags at the top of
`<body>`, ahead of the app's own markup and its own script:

```html
<script src="https://www.gstatic.com/firebasejs/10.12.0/firebase-app-compat.js"></script>
<script src="https://www.gstatic.com/firebasejs/10.12.0/firebase-auth-compat.js"></script>
<script src="https://www.gstatic.com/firebasejs/10.12.0/firebase-firestore-compat.js"></script>
```

That is 528 KB raw / 159 KB gzipped of cross-origin JavaScript the HTML parser
had to fetch and execute before a single row of the scorecard existed. It is
cross-origin, so `sw.js`'s fetch handler never sees it and it is never
precached — every launch whose HTTP cache had expired went to the network for
it. And none of it is needed to keep score: sign-in is optional, local storage
is the source of truth, and a signed-out player never touches Firebase at all.

Measured, serving the bundles locally so only their *position* differs:

| Cold launch | Before | After |
| --- | --- | --- |
| Each bundle stalls 1.5 s (weak link, parallel fetch) | first paint **1596 ms** | first paint **120 ms** |
| Host accepts the connection and never answers (a dead zone — `navigator.onLine` is still `true`, so nothing short-circuits) | **still blank at 20 s** | usable at **124 ms** |

The second row is the real one. In a dead zone the app showed a blank screen
for as long as the browser was willing to wait, on a course, which is the one
place it matters.

**Fix.** The SDK is listed in a `FIREBASE_SDK` array and fetched by
`ensureFirebase()` on idle, after the first screen is up — and not at all while
`navigator.onLine` is `false`, with an `online` listener so a phone that finds
signal on the 4th tee picks sync up without a relaunch. Sign-in, joining a live
round, and opening a `?watch=` link `await ensureFirebase()` themselves. A
failed load clears the promise so the next tap retries.

Three consequences worth knowing:

- `bindFirebaseAuth()` was a bare top-level statement that only worked because
  a blocking script had already defined `auth`. It is now a function the loader
  calls.
- `scripts/build-preview.py` rewrites the `FIREBASE_SDK` array rather than
  deleting script tags, so the loader, the retry, and every
  `await ensureFirebase()` call site are the same code paths in test as in
  production. The emulator build hooks `window.__FB_AFTER_INIT__` instead of
  injecting at a text offset after `firebase.initializeApp(` — initialisation
  now happens inside a promise, so there is no longer a point in the source
  that is also a point in time.
- A signed-in player would have watched "Sign in to sync your rounds across
  devices" for the first second of every launch while the SDK loaded. The auth
  bar now draws from a cached display name and photo and the live callback
  corrects it; offline, where the callback never comes, that cache is also the
  honest answer.

### 2. The screen slept through every round

There was no wake lock anywhere in the app. A round is four hours of walking
between thirty-second bursts of typing, so the phone locked itself between
every shot: unlock, reopen, find the hole, enter the score, eighteen times.
This is the single largest quality-of-life gap against anything else in the
category.

**Fix.** A screen wake lock is held for exactly as long as a round is the thing
on screen — scoring, or watching someone else's — and dropped the moment it is
not, so nothing is held on the home screen or in Settings. The system releases
the lock whenever the page is hidden and does not restore it, so it is
re-requested on `visibilitychange`. Settings → Round Defaults carries a
**Keep Screen Awake** switch for anyone who would rather have the battery.

Everything is best-effort: no API, a permissions-policy block, or a rejected
request all leave the app exactly as it was.

### 3. Pinch-zoom was switched off app-wide

Called in `design-ideas.md` §3d, confirmed here and fixed. The viewport carried
`maximum-scale=1.0, user-scalable=no`. That was the old fix for iOS zooming in
on a focused sub-16 px field; #100 replaced it properly with a 16 px floor on
every control under `@media (pointer:coarse)`, which is still there. So the
lock had exactly one effect left — Android honours `user-scalable=no`, so the
app could not be pinch-zoomed at all. WCAG 1.4.4, on a dense numeric table read
outdoors by people who mostly need reading glasses.

### 4. Confirming a hole invented scores, silently

`design-ideas-2.md` §F3, still live, and the most serious of the three because
it moves money:

```js
state.scores[a][e] = null != _sv[a] ? _sv[a] : state.pars[e]
```

The dashed 50 %-opacity chip under an unscored player *looked* like a
placeholder and *became* a real score on confirm, with no prompt, and the
hole's money settled on it. `finishRound()` already asks before fabricating par
for unplayed holes.

**Fix.** Per-hole confirm now names the specific people about to be given a par
and says what it costs — "Nick and Dana have no score on this hole. Confirming
records par (4) each, and the money settles on that."

### 5. Every score tap deep-copied nine objects

`pushUndo()` ran nine `JSON.parse(JSON.stringify(...))` round-trips on every
tap of the stepper, every bonus button and every hammer, and kept thirty of
them. Two changes:

- `structuredClone` where available (native deep copy, no string in the
  middle), with the JSON path kept as the fallback.
- A run of edits to one cell now coalesces into one undo step. Holding `+` from
  4 to 9 used to push five snapshots, so undoing that one score cost five taps
  of Undo — and evicted five real steps off a 30-deep stack.

## Not shipped, in the order I would take them

### A. `saveCurrentRound()` rewrites the whole history on a 1 s debounce

Every save parses the entire `golfRounds` blob, replaces one key and
re-stringifies all of it, once a second while anyone is entering scores.

Measured: **2.3 KB per round**, so a 100-round season is a ~230 KB
parse-and-stringify per save. That is ~0.2 ms per save at the 9-round demo
size on a desktop and grows linearly; call it tens of milliseconds on an old
phone after a couple of seasons. Not urgent, and worth knowing before it is.

The real fix is one localStorage key per round, which touches `getAllRounds`,
`loadRound`, `deleteRound`, `saveFinishedRound`, `exportAllData`,
`handleImportFile` and the Firestore sync, and needs a migration. It is a
deliberate piece of work, not a drive-by.

At 5 MB of quota and 2.3 KB a round the ceiling is ~2,100 rounds, so quota
exhaustion is roughly twenty years of heavy play away. Worth noting that
`safeSetItem` currently returns `false` on a quota failure and every caller
ignores it: the round in progress would stop persisting behind a toast. The
ceiling is distant but the failure mode is silent, which is the wrong shape.

### B. `renderHole()` rebuilds the whole scoring screen on every tap

One `innerHTML` assignment for every score row, then `renderGameStatus()`,
`renderHolePreview()`, `renderHoleMoneyLog()`, `renderPlayFeed()` and
`renderHoleDots()` — for a `+1` on one player. The money itself is already
memoised (`_moneyCache`), so this is DOM cost, not arithmetic, but it also
throws away focus and any open disclosure state on each tap.

The cheap 80 % is to update the tapped row's number, class and net label in
place and only fall back to the full rebuild when the set of rows or sections
changes.

### C. Six `setInterval(..., 100)` monkey-patch pollers

The Firestore sync wrappers are installed by six intervals that poll for
functions that are already hoisted and defined in the same script. They clear
on their first tick, so this is not a leak — but for the first 100 ms after
load `saveCurrentRound` and friends are unwrapped, and the pattern is load-
bearing in a way nothing states. They can be direct calls.

### D. Still open from the earlier rounds

Worth re-reading with this pass's evidence attached:

- **`design-ideas-2.md` §F1/F2** — the stepper and the quick picker disagree
  about auto-advance and about range, and there is still no way to record a
  pick-up. People invent a 9 and the money engine settles on it. §F3 above was
  the third symptom of the same root: nothing in the scoring row distinguishes
  "this is what happened" from "this is a guess".
- **`design-ideas-2.md` §F4** — the quick picker is a modal that is not one: no
  `role="dialog"`, no scrim, Escape does not close it, and a dismissing tap can
  also hit a `+` behind it and change a score.
- **`design-ideas-2.md` §A** — the app is called "Settle up" and cannot tell
  you whether you got paid.

(`design-ideas.md` §3a is done — `initDarkMode()` falls back to
`prefers-color-scheme` when no skin has been chosen. Worth striking from that
list.)

### E. Smaller things

- The service worker refetches the full 585 KB shell on every launch to detect
  a deploy. It is a background revalidate and the cached shell is served
  immediately, so it costs nobody a wait — but it is 185 KB gzipped of a
  metered connection per launch, and a `HEAD`/`ETag` check would answer the
  same question.
- `role="button"` elements get Enter/Space from a global delegate, which is
  good. The delegate keys off `[role="button"][tabindex="0"]` exactly, so any
  future `role` needs adding to it — `role="switch"` was added this pass for
  the wake-lock toggle. The Broadcast Skin row is still a `role="button"` that
  behaves like a switch.
